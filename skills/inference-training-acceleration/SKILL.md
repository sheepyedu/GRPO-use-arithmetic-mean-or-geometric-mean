# 推理与训练提速

从真实瓶颈选择改动，用同一工作负载核验收益，再接回任务正常入口。沿用用户对模型、数据、科学预算、资源和运行方式的约定。服务器连接和资源操作采用当前环境对应的访问流程。

## 先确定优化目标与基线

确认用户关心的是单请求延迟、吞吐、每轮时间、总完成时间、显存容量还是单位有效结果成本。固定墙钟预算时，吞吐提升可能增加完成轮数；固定轮数时才直接减少训练时间。记录加载、编译、预热及最终评测是否计入。

读取当前源码、配置、完整日志和进程身份，定位正在执行的任务及其检查点边界。实验进行中先准备独立候选版本，按现有恢复能力安排切换。核实空闲设备、磁盘及其他任务的归属，避免把进程启动或GPU繁忙当作完整训练成功。

按任务实际阶段拆分时间，例如数据准备、prefill、decode、rollout、行为/参考评分、前向反向、optimizer、CPU/GPU迁移、checkpoint、验证测试及同步等待。保留事件含义，step结束时打点会将首step计入前段，并将后续保存计入本段。

对单个串行进程的JSONL事件，可用以下助手汇总相邻事件区间。在本Skill目录运行，或按实际安装位置使用脚本绝对路径。多个并发文件分别报告，累计进程秒不直接代表整批墙钟或GPU小时。

```sh
python scripts/profile_events.py /path/run-a/events.jsonl /path/run-b/events.jsonl
```

脚本默认将区间归给前一个事件的phase。若日志phase表示刚结束的阶段，使用 `--interval-owner next`。最后一个事件之后的时长需另有终态证据。异步重叠阶段应结合CUDA Event、profiler或追踪系统解释，计时实验在所测边界同步GPU，常规训练保留异步执行。

## 根据瓶颈选择候选

| 主要成本 | 候选方法 | 需要核实的条件 |
|---|---|---|
| decode与CPU调度 | CUDA Graph、编译、连续批处理、增加请求槽 | 形状/LoRA兼容、图捕获显存、CPU开销、初始化成本、尾延迟 |
| prefill或长输入 | chunked prefill、合理批token预算、可复用前缀缓存 | 提示共享程度、实际缓存命中、KV容量及长短请求公平性 |
| 前向反向 | 合适的attention内核、显存充足时减少梯度重计算、微批或packing | 长度分布、峰值显存、padding浪费、mask/position与每样本归一化 |
| 词表概率统计 | 复用归一化结果、跳过未消费的熵/统计、融合算子 | 输出logprob、梯度、KL与熵的语义、精度和实际kernel收益 |
| GPU/CPU同步 | detach后延迟汇总诊断、减少逐条item/float/cpu、合理搬运 | 及时暴露非有限值，避免保留计算图导致显存增长 |
| 数据和序列化 | 预分词、并行准备、合适存储、减少重复解析 | 源码/模板版本、数据顺序、进程安全、缓存失效 |
| 保存与迁移 | 减少冗余拷贝、异步落盘、调整保存方式 | 稳定快照、optimizer/scheduler/RNG完整、COMMITTED时机、恢复能力 |
| 分布式同步或通信 | 检查rank等待、负载均衡、拓扑和通信重叠 | 最慢rank、同步正确性、有效batch及故障传播 |

先估算优化上限。若某段占总时间f、该段加速s倍，理想端到端加速约为 `1 / ((1-f) + f/s)`。不同阶段的比例和重叠要与计时口径一致。

## 验证优化是否值得采用

- 尽可能固定模型与权重、输入token、长度分布、任务数、输出上限、软件版本和设备条件。计数实际输出token，生成长度发生变化时同时报告总耗时与吞吐。
- 记录冷启动与预热后结果，进行适量重复。合并吞吐用总token除以总时间。共享硬件或编译缓存条件变化时，说明比较限制。
- 对训练改动比较逐样本logprob、mask、优势、损失及梯度，必要时核对一次真实optimizer更新和状态保存。容差结合dtype、误差量级、参数尺度和训练目标决定，接近零的梯度同时看绝对误差。先定义判据再判断候选，避免为通过测试放宽标准。
- 变长批处理核对attention mask、position、completion偏移及loss分母。改变microbatch时保留原minibatch的权重和optimizer更新次数。零奖励优势样本的KL项仍可能有梯度。
- 显存测量同时记录框架峰值allocated/reserved和设备总占用，覆盖代表性短长序列及边界长度。按实测条件选检查点阈值、请求槽和批token数。
- 验证图捕获/编译与实际LoRA加载、adapter更新、sleep/wake、checkpoint恢复的组合。冷启动通过后检查正式入口的第一轮完整更新。
- 候选更慢、收益小或数值变化难以解释时，保留证据并选择其他方法。短测结果只有在实际任务复测后才支持整轮或整批收益声明。

## 接回任务并保存可复用结论

通过项目已有测试和针对改动的回归检查后，记录候选源码/配置版本、实际依赖、输入、时间、峰值显存、数值差异和原始回执。涉及多因素联合改动时，按联合设置报告加速倍数。

按现有授权启动或恢复任务，确认真实PID、阶段、首轮提交、完整状态和失败记录。派发响应不明时先读取真实效果，避免重复训练。已完成的正式实验保留原结果；后端变更引起的数值轨迹与科学预算差异写入跨run比较。

正式任务继续执行时沿用已有监督间隔和项目进度工具，发现真实失败及时定位并修复。汇报包括原瓶颈、采纳/撤回的改动、验证范围、实测收益、尚未测量的指标及当前任务位置。
